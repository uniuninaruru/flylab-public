Phases of the full-graph jobs (B1): load processed graph 0.42 s, populations 0.02 s, sign mapping
0.46 s, network build 0.78 s, engine init + copy to the GPU 0.92 s. 2.95 % of the neurons spiked at

Platform, from the records: RTX 5070, compute capability 12.0, 12,227 MiB, of which 2,122 MiB
were already used by other processes (desktop, homelab services) before the run; torch 2.15.0
(CUDA 13.2 build); WSL2 kernel 6.18.33.2; AMD Ryzen 7 9700X (8 logical CPUs visible to WSL);
WSL VM RAM 15.2 GiB; container memory limit 6 GiB. `nvidia-smi` lists the FlyLab process but
reports its memory as `[N/A]` under WSL2 (Q20). The allocated/reserved figures above describe
torch's allocator, which excludes CUDA context, loaded kernel images and allocations made
outside that allocator. They are not a measurement of total process VRAM.

[PR-03 review finding 8](../audit/PR-03-review.md#finding-8--vram-is-reported-from-torchs-allocator-only-about-200-mib-per-run-is-not-counted)
compares the committed device-wide `nvidia-smi` readings before and while loaded with these
allocator peaks. Their increase includes other processes; attributing the excess to FlyLab's
CUDA overhead is an inference. Future benchmark records also sample free/total device memory
with `torch.cuda.mem_get_info()` before engine initialization, after initialization and at the
end, and report device-wide deltas next to allocator peaks (see
[benchmark protocol](../BENCHMARK_PROTOCOL.md)). These
samples can miss a transient peak, and a first CUDA query can initialize context resources
before the baseline. The existing evidence records and their numbers are unchanged; the new
accounting is **UNVERIFIED on the RTX host** pending the next run.

## Performance finding (not an M3 gate)

**The CUDA engine is correct and small, but slow: about 0.036 simulated seconds per wall second on
the full graph (≈ 28 s per simulated second), and about 5.5 × slower than the NumPy reference on
the same host CPU (B1: 2.97 s vs 0.54 s median).**

`profile-B1-20261104T101336Z.json` (torch.profiler, 300 steps after 200 warm-up steps; the profiler
inflates host times) originally attributed the step as follows:

- **322 µs of device time per step is over-counted**: the old summarizer adds CPU operation rows
  and the device kernel rows that represent the same work;
- the host issues **110 kernel launches and 8 stream synchronizations per step**;
  `cudaLaunchKernel` alone accounts for about half of the host time;
- **8 device→host copies per step was a direction-label error**: the old summarizer counts
  `cudaMemcpyAsync` calls without distinguishing host→device from device→host.

Re-profiled on 2026-11-09 with the corrected summarizer (`profile-B1-eager-20261109T064934Z.json`,
same eager engine code, PR-03b commit `087fd90`): **162.5 µs of device time per step**, 110 kernel
launches, 8 synchronizations, 1 host→device and 7 device→host copies per step. See
[`M3b.md`](M3b.md) for the fused engine that removes this overhead, and
[PR-03 review finding 7](../audit/PR-03-review.md#finding-7--profile_steppy-counts-gpu-time-twice-m3q22-say-322-µs-per-step).
The original profile JSON remains unchanged. Launch and synchronization latency dominate the
step (made worse by WSL2). This is the correctness-first design of spec
7.3 (gather + `index_add_`, one host round trip per 0.1 ms step). Optimization — fewer host
synchronizations (fixed-size buffers instead of `nonzero`/`int(...)`), fused kernels, CUDA Graphs,
recording spikes in batches — is a separate PR, checked against the same parity tests (Q22);
it is PR-03b ([`M3b.md`](M3b.md)).
Wall times vary between repeats (e.g. B0: IQR 0.76 s on a 1.78 s median) because the GPU host also
runs a desktop and homelab services.

## What is not claimed

- The B1/B2 workload (100 Hz forced spikes into every `class == gustatory` neuron, ASSUMED
  transmitter sign mapping, uniform LIF parameters, `w_syn` ASSUMED) is an **engineering load**,
  not a taste experiment. Its spike counts say nothing about fly physiology.
- Spike identity was measured for these workloads and seeds; it is not promised for other
  inputs, dtypes or library versions (MODEL_ASSUMPTIONS 2.3 states the margins that apply).
- B0-1s drives the network only during 10–100 ms, so most of its second is quiet; it shows that a
  1 s synthetic run finishes, not throughput under load.
